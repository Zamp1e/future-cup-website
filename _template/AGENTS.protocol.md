# AGENTS.protocol.md — 项目档案生成协议（模板，不进项目）

## 0. 角色与目标

你是工程助手，唯一任务是把实验目录变成"下次会话进来就能直接开工"的项目档案：`<工作目录>\AGENTS.md`，行数按 §4.3 档位控制（常规 60–100），由 `AGENTS.templates\generated.md` 空壳逐项填写。
收尾用 3–5 行说明写了什么、哪几项待确认。本文件是模板，放在 `_template\` 这类子目录（或仓库外），**不要放到仓库根，更不要复制成根 AGENTS.md**。

## 1. 什么时候执行

满足任一条即执行 §3：PROFILE 区块为空或仍是「（未填写）」；用户说"把这个实验做了 / 按题目要求实现 / 帮我写这个作业"；目录里新出现题目材料（`.docx` / `.pdf` / `.doc` / `.txt`）或新子工程；换了实现语言或新增辅助脚本语言；用户说"重新了解这个项目 / 更新 AGENTS"。

任一条都不满足 → **不要提问**，直接读项目 PROFILE 开工。重复提问是最招人烦的失败。

## 2. 项目档案字段（唯一真相源）

PROFILE 表只能有这 10 行，顺序不变；值必须具体，不能是口号。

| 字段 | 填什么 | 合格标准 |
|---|---|---|
| 项目定位 | 做什么 + 交付给谁 | 能回答"这是啥、给谁交"，不是口号 |
| 交付物 | 代码 / 代码+报告 / 只改报告 | 形态与格式明确 |
| 组织方式 | 几处工程、目录怎么分 | 目录规则可执行（模式化，如 `<前缀><序号>/`） |
| 技术栈 | 语言 + 版本 + 构建工具，每个语言后注 `（模块名）` 或 `（临时栈约束）` | 三者齐全；注模块名的文件必须存在；一次性项目注「临时栈约束」并在「规则模块」节写清 |
| 构建验证 | 一条可直接复制的命令 | 贴上就能跑，不需口头补充 |
| 硬约束 | 题目明确的禁止/要求：样式文件、第三方库、命名 | 逐条可判定 |
| 禁区 | 不许改的文件/目录 | 给出路径或目录名 |
| 截图策略 | 谁产出、怎么拿到；无截图需求写「无」 | 有截图时必须写清责任人与交付方式；「无」视为已填 |
| 进度 | 已完成 / 待做 | 列出已完成项与剩余项 |
| 待确认 | 未定、下次要问的点 | 至少一条，或写"无未决项" |

## 3. 三步启动协议

### 第 1 步 勘察（只读，不提问）

1. 目录树 2–3 层，跳过依赖与产物目录（`node_modules`、`build`、`.git`、`.idea` 之类，以及本项目自己的依赖目录）。
2. 找标志文件判断技术栈与构建方式（`package.json`、`hvigorfile.ts`、`tsconfig.json`、`requirements.txt`、`pom.xml`、`*.cpp`/`*.h`、`CMakeLists.txt`）。
3. 读 `README.md` 与题目材料，列出任务清单与已完成项。
4. 探编译器/设备：`<构建工具> --version`、`<设备或模拟器探测命令>`，按技术栈与平台挑。
5. 目录里有 Office 文档时先探测 Office 工具；不可用就提醒用户装插件，不手搓解析。
6. 产出 3–5 行结论：技术栈、构建方式、任务列表、当前进度；不确定的留给第 2 步。
7. 用 `find . -maxdepth 2 -type d` 取一层半目录，作为第 3 步「目录地图」的备料。

**勘察能看出来的，一律不问**：语言、版本、目录结构、构建命令。

### 第 2 步 一次问清（≤5 题）

一次提交全部问题，每题首项标「（推荐）」。默认值：代码+报告 / 每实验独立子目录 / 编译零错误 + 样例输出逐字一致 / 纯标准库 / 无设备时截图由用户提供。
约束题必须覆盖三类：**样式文件（是否允许 CSS）**、第三方库、目录与文件命名。用户跳过某题 → 用默认值，并在 PROFILE 记为 `（默认，未确认）`。

话术照抄，只替换尖括号；先给一句勘察结论再列题：

```text
我先看了目录：<一句话结论>。有几件事只有你知道，答完我就开工：
1. 这是什么项目？题目材料在哪？（<推荐项>（推荐）/ <其他选项>）
2. 交付什么？（<推荐项>（推荐）/ <其他选项>）
3. 怎么组织？（<推荐项>（推荐）/ <其他选项>）
4. 怎么算通过？（<推荐项>（推荐）/ <其他选项>）
5. 有什么硬性限制？（<默认约束>（推荐）/ <其他>）
```

### 第 3 步 落盘

1. 已有旧档案则备份为 `AGENTS.md.bak.<日期>`；没有就直接新建。
2. 按 §2 填 PROFILE；按 §4 从 `_template\` 的空壳生成；规则模块只取一个（或用「临时栈约束」替代）。
3. 先写 `AGENTS.md.tmp`（同目录；这个后缀不会被自动加载），UTF-8 无 BOM。
4. 跑 §5 自检并真跑一次 PROFILE「构建验证」命令；形式全绿、命令跑通才 `mv AGENTS.md.tmp AGENTS.md` 改名。语义正确性（技术栈判错、硬约束失真、模块摘错条目）自检查不出，必须在摘要里逐条说明并请用户拍板。改名失败（权限/沙箱）→ 保留 `.tmp`，把这条命令原样给用户，并在摘要注明"尚未生效"。
5. 给用户 3–5 行摘要 + 一句"有要改的吗"。

## 4. 产物规格（硬规则）

### 4.1 必须包含（多一项都不行）

1. 标题 + 2–3 行说明：本文件是项目档案；协议模板在 `_template\AGENTS.protocol.md`；技术栈规则在 `_template\AGENTS.modules\`；新增材料时回模板重新勘察。
2. PROFILE 区块，10 行填满，无「（未填写）」；「技术栈」每个语言后注模块名或「（临时栈约束）」。
3. 工作准则 5–8 条（照 §6 精简，不改语义）。
4. 仅启用的规则模块：从 `_template\AGENTS.modules\` 对应文件摘录；未启用的模块内容整条删除，不留"备用"。元规则不是模块内容，不在此条删除范围内（见第 5 条）。
5. 「规则模块」节下的元规则三行（照空壳原文写，只替换已启用清单）：第一行目录入口 + 已启用模块名，标明「快照」；第二行一次性项目——先列一次 `_template\AGENTS.modules\`，没有对应模块就在本节写 3–5 行「临时栈约束」（版本 / 构建命令 / 运行命令 / 主要限制 / 常见坑），不建库文件；第三行固化——第二个项目仍用到该栈时才问清那四项、用 `module-skeleton.md` 建模块、先给用户过目、再写进 PROFILE「技术栈」并登记。这是唯一允许出现未启用模块信息的地方，不许删。
6. 收尾约定：更新 PROFILE 进度/待确认 + 变更记录一行。
7. 变更记录表（日期 / 做了什么 / 为什么）——只存在于生成物，模板不记变更。
8. 若会新增独立子工程：一句「子目录先读 `../AGENTS.md`」。
9. 题目级限制（样式文件/CSS、第三方库、目录命名）必须落在 PROFILE「硬约束」里；模块只写默认做法，不能替用户定规则。
10. 目录地图（≤12 行）：一行一目录，写路径 / 用途 / 状态；路径必须真实存在，不列文件。目录超过 10 个或需要树形图 → 单独 `STRUCTURE.md`，根档案只留一行指向；两个文件都过校验。

### 4.2 名词白名单（唯一判据）

生成物里每个技术名词，必须能在 PROFILE 的「技术栈」或「构建验证」里找到来源。允许本项目技术栈、本项目真实使用的工具与命令、通用工程概念（编译、测试、目录、备份）；禁止任何未在 PROFILE 出现过的语言、框架、SDK、构建工具名称——写"以后可能用得上"也不行。找不到来源就删掉整句，不要改写成"参考用"。模板自身路径（`_template\...`）与元规则里的四类问项不算技术名词。

### 4.3 规模、强度、语言

- 行数按复杂度分三档，PROFILE 填完再定档：简单（单文件、无报告）40–70；常规 60–100；复杂（多工程或含报告）≤140。低于档位下限说明信息不足；超过 140 必须重写。
- 强度词只用「必须 / 禁止 / 只」；不写「应该 / 尽量 / 建议」。
- 中文；技术名词保留原文；不写口号式形容词。

## 5. 自检（生成后逐条跑，结果写进汇报）

**§5 只验形式，不验内容。** 行数、残留、字段、模块名、路径全对，不代表档案正确：技术栈判错、构建验证跑不通、硬约束转述失真、模块摘错条目，这几条自检永远发现不了。形式全绿 + smoke test 通过，只说明"可以交给人看"；内容正确性必须人工拍板。

```bash
cd <工作目录>
F=AGENTS.md.tmp        # 改名后复查时换成 AGENTS.md

wc -l "$F"                                          # 对照 §4.3 档位：40–70 / 60–100 / ≤140
grep -nE '（未填写）|\{\{|附录' "$F"                 # 必须 0 命中：模板残留
grep -nE '^规则按栈取 .*已启用：' "$F"              # 必须 ≥1 命中：元规则第一行
grep -nE '^栈不在库中' "$F"                         # 必须 ≥1 命中：元规则第二行
grep -nE '^\| (项目定位|技术栈|构建验证|进度|待确认) \|' "$F"   # 关键字段必须有值
sed -n '/已启用：/p' "$F" | grep -oE '[A-Za-z0-9_-]+\.md' | while read m; do test -f "_template/AGENTS.modules/$m" || echo "缺模块: $m"; done   # 必须无输出
sed -nE 's/^\| 技术栈 \| (.*) \|$/\1/p' "$F"          # 核对：每个语言后有（模块名）或（临时栈约束）
```

`README.md`、`AGENTS.modules`、`AGENTS.templates` 是合法内容（模块摘录本来就会提 `README.md`，元规则必须指名目录），不进禁词；禁词只查模板残留。

4) 名词白名单：把生成物里的技术名词抄成清单，逐个标注来源（PROFILE 哪个字段）；无来源的删除。
5) 目录地图校验：表中每条路径 `test -d` 必须成立；对不上就修正地图，不要靠"大概是这样"放行。
6) 技术栈 ↔ 模块对齐：每个语言后都有 `（模块名）` 或 `（临时栈约束）`；写了模块名的，该文件必须真实存在。
7) smoke test：把 PROFILE「构建验证」那条命令原样跑一次并贴输出；跑不通 → 修 PROFILE 或修项目后重跑，禁止带病改名。

脚本按 bash 写（Windows 用 Git Bash）；PowerShell 等价：`(Get-Content AGENTS.md).Count` 数行，`Test-Path` 验路径。

## 6. 通用工作准则（写进生成物时精简到 5–8 条）

1. 先看再改、最小改动：改前先读相关文件与题目原文；只动需求涉及的部分，不顺手重构能跑的代码。
2. 结构性问题先问：交付形态、工程数量、实现方式先确认；命名与写法自己定。
3. 先验证再声明：说"通过"前必须真跑过，贴命令与输出；没跑就说"未验证"。
4. 证据真实：截图与结果只能来自真实执行；产不出来直说并向用户索要。
5. 不臆造：路径、版本、API 查不到就说"未找到/不确定"。
6. 清临时文件：中间产物放临时目录，结束删除。
7. 不越界：不删他人文件、不改他人文档、不 commit/push、不擅自装全局依赖。
8. 先读目录地图再遍历：地图能回答的不要再 `ls`/`find`；地图与磁盘不符 → 先修正地图再干活。

## 7. 冲突与停手

- 优先级：用户当次指令 > 本模板 > 既往档案里的习惯做法。
- 工具/插件不可用：告知用户并等确认，禁止降级手搓（Word COM、OLE 解析）。
- 拿不准的写进「待确认」，不硬编结论；用户说"先别管这个文件"→ 立即停手，先确认新目标。

## 8. 关联文件与模块库

- `_template\AGENTS.modules\`：技术栈规则库，按 PROFILE「技术栈」**只读匹配的那一个**；不枚举、不预加载。清单是生成时快照，缺栈判定以目录实际文件为准。
- 缺栈默认**不建库文件**：一次性项目在产物「规则模块」节写「临时栈约束」3–5 行（见 §4.1 第 5 条）。
- 只有第二个项目仍用到该栈才固化：问清四件事——语言版本、构建工具、编译/运行命令、主要限制；用 `module-skeleton.md` 生成 `_template\AGENTS.modules\<stack>.md`（20–40 行，只写换题目也成立的事实与默认做法），先给用户看一眼再继续。
- 新模块自检：行数 ≤40、不含具体项目路径或人名、题目级限制仍归 PROFILE；不合格就重写，不硬塞。
- `_template\AGENTS.templates\generated.md` 是产物空壳；`module-skeleton.md` 是新模块骨架；`README.md` 只做导览，不承载规则。
- 模板目录缺失或被移走：不要凭记忆重造档案，直接告诉用户"找不到模板"，不要猜路径。

## 9. 增量更新协议（已有 AGENTS.md 时）

触发同 §1。**禁止**按 §3 从零重写覆盖已有档案。

1. 读现有 `AGENTS.md` 全文，按 §3 第 1 步只读勘察，列差异（新增目录 / 新材料 / 换语言 / 进度变化）。
2. 先给用户 diff：拟改哪几行、改成什么、为什么；确认后再动手。
3. 只补：PROFILE 的进度 / 待确认 / 技术栈 / 目录地图新增行；已有字段不改写，除非用户明确要求。
4. 现存模块正文只增不删；已验收实验的「禁区」与「已验收，勿改」状态不动。
5. 改动前备份 `AGENTS.md.bak.<日期>`；改完跑 §5（含 smoke test），变更记录必写一行。
6. 摘要写清：改了哪几处、没动哪几处、哪项待用户拍板。

## 10. 模板设计陷阱（自用备忘）

1. 把整份模板复制进项目 → 未启用模块被当项目规则加载。
2. 模板里写变更记录 → 带上了某个项目的日期与改动史。
3. 示例值写成具体技术栈 → 模型把示例当默认。
4. 黑名单表述 → 反而提高禁词出现率；用白名单 + 来源核对。
5. 强度混用 → 模型只执行更强那条。
6. 同一事实写多处 → 改一处漂移三处；规则只放本文件，README 只做导览。
7. 自检串与被检内容同行 → 检查恒通过或恒失败；自检命令不得包含它要检的字面串。
8. 把缺栈处理当未启用内容删掉 → 新栈无从下手（§4.1 第 5 条）。
9. 清单当实时事实 → 重复建模块 / 读空文件（清单是快照）。
10. 形式自检当正确性证明 → 错误档案被当真相加载；必须 smoke test + 人工拍板（§5）。
